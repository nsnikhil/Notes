### Bug 1: Checklist — Enter key creates duplicate items
**Root Cause (STILL BROKEN):** The `CheckListAdapter` subscribes to `text.editorActions()` in the ViewHolder `init` block. When the user presses Enter (IME_ACTION_NEXT), it calls `mOnAddClickListener.addClickListener()` → `NewNoteFragment.addCheckListItem()`. This adds a new `CheckListObject(text="", done=false)` to `mCheckList` and calls `submitList(mCheckList.toList())`. However, `CheckListDiffUtil.areItemsTheSame()` compares by `text` and `done` — so ALL empty items with `done=false` are considered the same item. When a second empty item is added, DiffUtil sees two items with identical identity (`text=""`, `done=false`) and produces incorrect diff results, causing visual duplication or item recycling bugs. Additionally, the `editorActions()` RxBinding subscription is created once per ViewHolder in `init` but ViewHolders are recycled — the subscription persists across rebinds, so a recycled ViewHolder can fire the callback for the wrong position. The combination of (a) no stable ID on `CheckListObject` and (b) `editorActions()` subscriptions surviving ViewHolder recycling is the double-add root cause.

**Fix required:** `CheckListObject` needs a unique stable ID field (e.g., `val id: String = UUID.randomUUID().toString()`). `CheckListDiffUtil.areItemsTheSame()` must compare by `id` only. The `editorActions()` subscription should either be re-created in `onBindViewHolder` or use a flag/guard to prevent duplicate firing.

### Bug 2: Camera — still does not work
**Root Cause (LIKELY FIXED but needs runtime verification):** The previous fix (ST-002) addressed the two known issues: (1) `file_paths.xml` was changed from `<external-path>` to `<external-files-path>` with `path="Pictures"` to match `getExternalFilesDir(Environment.DIRECTORY_PICTURES)`, and (2) the FileProvider authority now uses `${applicationId}.fileprovider` in both `AndroidManifest.xml` and `startCameraIntent()` via `BuildConfig.APPLICATION_ID`. The code path looks correct: `createImageFile()` creates a temp file in `getExternalFilesDir(DIRECTORY_PICTURES)`, `FileProvider.getUriForFile()` generates a content URI, and `cameraLauncher.launch(photoURI)` fires the camera intent. However, there is a remaining issue: `startCameraIntent()` is guarded by `checkPermission(WRITE_EXTERNAL_STORAGE, ...)`. On API 29+ (scoped storage), `WRITE_EXTERNAL_STORAGE` is automatically denied and the permission request dialog is never shown. Since `getExternalFilesDir()` does NOT require `WRITE_EXTERNAL_STORAGE`, the permission check is unnecessary and actively blocks the camera on modern devices. The `checkPermission` call will call `ActivityCompat.requestPermissions()` which on API 29+ will immediately deny, and the `action()` callback (`startCameraIntent`) is never invoked.

**Fix required:** Remove the `WRITE_EXTERNAL_STORAGE` permission check wrapping `startCameraIntent()`. Call `startCameraIntent()` directly (same pattern already applied to the gallery launcher in the current code).

### Bug 3: Lock — does not work on first attempt
**Root Cause (STILL BROKEN):** The flow is: `setLock(item)` calls `PasswordUtil.checkLock()`. If no password exists, `checkLock()` shows the `PasswordDialogFragment` and returns `false`. Because it returns `false`, `setMenuState()` is NOT called — the lock icon does not toggle. The user sets a password in the dialog, which calls `savePassword()` → `parentFragmentManager.setFragmentResult(REQUEST_KEY, ...)`. The `NewNoteFragment` has a `FragmentResultListener` that receives this result and calls `setMenuState(mIsLocked, item, ...)`. However, the `mLockMenu` variable is captured from `onCreateOptionsMenu` and the listener uses `mLockMenu?.let { item -> ... }`. This part looks correct. The ACTUAL remaining bug is a race condition: `PasswordUtil.checkLock()` returns `false` synchronously, so `setLock()` returns without toggling. The `FragmentResultListener` should then toggle the lock when the password is created. BUT the listener calls `setMenuState(mIsLocked, item, ...)` which returns the new state — however, the return value is assigned to `mIsLocked` correctly. So the FragmentResult path SHOULD work. Let me re-examine: the `FragmentResultListener` is registered in `onViewCreated` with `viewLifecycleOwner`. The `PasswordDialogFragment` calls `parentFragmentManager.setFragmentResult()` in `savePassword()` and then `dismiss()`. The result is delivered synchronously when the dialog dismisses. This should work. HOWEVER — there is a subtle issue: `PasswordUtil.decryptAndGet()` in `PasswordDialogFragment.initialize()` uses `observe(viewLifecycleOwner, ...)` with an async RxJava `Single.fromCallable` on `Schedulers.io()`. The `value` field is set asynchronously. If the user is fast, `value` might still be `"NA"` (default) when they tap "Save", causing `addNewPassWord()` to be called (correct path). But the real issue is: when `checkLock()` returns `false` on first tap, the lock does NOT toggle. The `FragmentResultListener` then toggles it. So the lock DOES toggle on first tap — but only after the password dialog completes. If the dialog is dismissed without setting a password (cancel), the lock correctly does not toggle. This flow appears correct IF the `FragmentResultListener` fires. The bug may be that on the SECOND tap (after password exists), `checkLock()` returns `true` and `setMenuState` toggles — this works. On the FIRST tap, `checkLock()` returns `false`, dialog shows, password is set, `FragmentResult` fires, lock toggles. This SHOULD work. The remaining question is whether the `FragmentResultListener` is actually receiving the result. One potential issue: `PasswordDialogFragment` is shown with `parentFragmentManager` from `NewNoteFragment`, but the `FragmentResultListener` is also registered on `parentFragmentManager`. If `PasswordDialogFragment` uses its own `parentFragmentManager` (which would be the hosting activity's FragmentManager for a DialogFragment), the result key might not match. Actually, for a DialogFragment shown via `fragmentManager.show()`, `parentFragmentManager` inside the DialogFragment IS the same FragmentManager that was used to show it. So if `NewNoteFragment` uses `parentFragmentManager` to show the dialog AND to register the listener, they should match. But wait — `PasswordUtil.showPasswordDialog(fragmentManager, tag)` receives `parentFragmentManager` from `NewNoteFragment.setLock()` which passes `parentFragmentManager`. Inside `PasswordDialogFragment.savePassword()`, it calls `parentFragmentManager.setFragmentResult(...)`. The `parentFragmentManager` of the DialogFragment is the FragmentManager that was used to show it — which is `NewNoteFragment`'s `parentFragmentManager` (the activity's FragmentManager). The listener in `NewNoteFragment` is registered on `parentFragmentManager` (also the activity's FragmentManager). So they DO match. The flow should work. The bug might actually be fixed by the current code. This needs runtime verification via Espresso test.

The fix requires adding a unique ID field to `CheckListObject`. This changes the serialized format of checklist data.
